## Назначение проекта

Приложение решает следующие задачи:

- показывает карту станций и их базовые параметры;
- предоставляет страницу с паспортом станции;
- отображает и позволяет скачивать годовые отчеты о полноте RINEX;
- содержит формы входа и регистрации;
- содержит административный раздел интерфейса (в текущем состоянии роль задается в коде).

На текущем этапе основная часть данных берется из локальных файлов и констант проекта.

## Архитектура приложения

### Общая схема

- Точка входа: `src/main.tsx`
- Корневой компонент: `src/App.tsx`
- Глобальные провайдеры:
  - `AuthProvider` (`src/context/AuthContext.tsx`)
  - `StationProvider` (`src/context/StationContext.tsx`)
- Роутинг: `BrowserRouter` + `Routes`

### Архитектурный подход

- `pages` – экранные компоненты/страницы;
- `modules` – крупные функциональные блоки (например, карта, карточки станций);
- `components` – переиспользуемые UI-элементы;
- `context` – состояние приложения, доступное на уровне дерева React;
- `services` – слой получения/преобразования данных.

## Маршруты и входные параметры

Основные маршруты из `App.tsx`:

- `/` → редирект на `/Map`
- `/Map` – карта сети
- `/Reports` – годовые отчеты
- `/Stations` – список станций
- `/Stations/:stationName` – паспорт станции
- `/Department` – страница отдела
- `/Login` – форма входа
- `/Registration` – форма регистрации
- `/Admin` – панель администратора (только при `user.role === 'admin'`)

### Входные параметры приложения

1. **Route params**
   - `stationName` в `/Stations/:stationName`

2. **Navigation state**
   - при переходе из списка/карты в паспорт передается объект `stationData` через `navigate(..., { state })`

3. **Пользовательский ввод**
   - формы `Login` и `Registration` (валидация через `react-hook-form`)

4. **Данные отчетов**
   - выбор года на странице `/Reports` формирует путь к статическому HTML-отчету

## Работа с данными и API

### Текущее состояние

- Основные данные станций загружаются из:
  - `src/constants/constants.ts` (базовые станции),
  - `src/constants/IGSNetwork.json` (дополнительные IGS-поля),
  - `src/constants/passports/*.txt` (sitelog/паспорт станции),
  - `public/reports/*.html` (годовые отчеты).

- Сервис `src/services/dataService.ts` в текущем виде возвращает локальные JSON-данные.

### Правила работы с API (для дальнейшей интеграции backend)

1. Все сетевые запросы добавлять в `src/services/*`.
2. Не выполнять HTTP-запросы напрямую внутри `components`/`pages`.
3. Типизировать ответы API через `src/types/types.ts` или отдельные файлы типов.
4. Обрабатывать ошибки на уровне сервиса:
   - нормализованный `throw new Error(...)`,
   - прозрачные сообщения для UI.
5. Не смешивать формат данных API и UI-модель:
   - делать явное преобразование DTO -> UI model.
6. Использовать единый подход к авторизации (после внедрения реального Auth):
   - токен/сессия в одном месте,
   - централизованная подстановка заголовков.

### TypeScript

- `strict: true`;

- обязательно поддерживать корректную типизацию пропсов, контекстов и сервисов.

### ESLint

Ключевые правила:

- `no-unused-vars` выключен в пользу `@typescript-eslint/no-unused-vars`;

### Prettier

Базовые настройки:

- `singleQuote: true`
- `semi: true`

- `printWidth: 100`


## Логика работы приложения

### 1. Инициализация

- Приложение поднимается в `main.tsx`.
- Подключаются провайдеры `AuthProvider` и `StationProvider`.
- Роутинг работает через `BrowserRouter`.

### 2. Загрузка станций

- `StationProvider` объединяет базовые станции и IGS-данные.
- Для каждой станции формируется итоговый объект с координатами и метаданными.
- Этот список используется на страницах карты и списка станций.

### 3. Навигация к паспорту станции

- При клике на станцию выполняется `handleRedirect`.
- В URL уходит `stationName`, в `location.state` передается `stationData`.
- На странице станции данные отображаются в табличной форме + мини-карта + ссылка на sitelog.

### 4. Отчеты

- Раздел `/Reports` строит имя файла отчета по выбранному году.
- Отчет открывается из `public/reports/` и может быть скачан.

### 5. Доступ к административной панели

- Маршрут `/Admin` показывается только при роли `admin`.
- На текущем этапе роль задается в коде (`AuthContext`) и не связана с backend-auth.

## Known limitations

Ниже перечислены текущие ограничения реализации, которые важно учитывать при разработке и эксплуатации.

### 1) Зависимость `StationPage` от `location.state`

- Страница `/Stations/:stationName` ожидает `stationData` в `location.state`.
- При прямом открытии URL, обновлении страницы или переходе по внешней ссылке `state` может отсутствовать.
- Следствие: часть данных на странице станции может быть неполной/пустой.
- Текущий обходной путь: открывать паспорт станции через `/Stations` или `/Map`.
- Рекомендуемая доработка: добавить fallback-загрузку по `stationName` (поиск в `StationContext` или загрузка из API).

### 2) Роль пользователя задается вручную в коде

- В `AuthContext` роль пользователя устанавливается статически (без backend).
- Ограничение: доступ к `/Admin` не защищен серверной авторизацией.
- Следствие: это UI-ограничение, но не полноценная модель безопасности.

### 3) Отсутствует полноценная backend-интеграция

- Основные данные сейчас приходят из локальных констант и JSON-файлов.
- Формы входа/регистрации не выполняют реальный обмен с сервером.
- Ограничение: нельзя считать текущую реализацию production-auth или production-data-layer.

### 4) Нет автоматизированных тестов и CI/CD

- В репозитории нет тестовых сценариев (unit/integration/e2e) и pipeline для автопроверок.
- Следствие: качество релиза зависит от ручной проверки перед деплоем.

### 5) Зависимость карты от внешних тайл-сервисов

- Карта использует внешний tile-provider.
- В закрытых сетях/при проблемах с доступом базовый слой карты может не загрузиться.

### 6) Отчеты ограничены набором статических файлов

- Раздел `/Reports` работает только с файлами, реально лежащими в `public/reports`.
- Если файл за выбранный год отсутствует, отчет недоступен.

## Troubleshooting (Если все сломалось)

### Проблема: проект не стартует после `npm install`

Проверить:

1. Версию `node -v` и `npm -v`.
2. Что запуск идет из корня проекта (`package.json` должен быть рядом).
3. Повторить установку:

```bash
rm -rf node_modules package-lock.json
npm install
```

### Проблема: белый экран / не рендерится страница

Проверить:

1. Ошибки в DevTools Console.
2. Ошибки типов:

```bash
npm run type-check
```

3. Ошибки линтера:

```bash
npm run lint
```

### Проблема: не открывается `/Admin`

- В текущей реализации роль задается вручную в `src/context/AuthContext.tsx`.
- Убедитесь, что выставлена роль `admin`.

### Проблема: паспорт станции неполный или пустой при прямом переходе по URL

- На странице `/Stations/:stationName` часть данных приходит через `location.state.stationData`.
- При прямом открытии URL (без перехода из списка/карты) `state` может отсутствовать.
- Решение: переходить из `/Stations` или `/Map`, либо доработать fallback-загрузку по `stationName`.

### Проблема: не загружаются карты/тайлы

- Проверить доступ к внешнему tile-серверу (`cartocdn`).
- Проверить сетевые ограничения/прокси.

### Проблема: нет отчета за выбранный год

- Файл отчета должен существовать в `public/reports/`.
- Имя файла должно соответствовать шаблону:
  - `completeness_report_<year>_001_365.html`
  - `completeness_report_<year>_001_366.html`

### Проблема: "поехали" стили

Проверить:

```bash
npm run format
npm run lint
```

И убедиться, что SCSS-импорты и BEM-классы не нарушены.
